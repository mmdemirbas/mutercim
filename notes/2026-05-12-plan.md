# Revised plan — Option B-lite

User feedback that shaped this revision:

1. **Don't remove any logic before proving new alternatives are better in all aspects.** Both paths exist in parallel; old paths stay default until proven inferior on the user's real workload.
2. **Granular control preserved.** Collapse only the *external* surface (CLI shortcut, config preset); internal phases remain individually runnable.
3. **Local-first enforced in code.** Cloud providers require explicit `allow_cloud: true` opt-in. Failover chain never auto-falls-back to cloud.
4. **License doesn't matter for model pick** — pick best quality (Gemma 3 family is fine).
5. **Arabic 2-col is not a P0** — primary mental target is Arabic Islamic books; multi-column happens but not common. RTL fixup is part of language-agnostic surface, not a special case in the parse phase.

---

## Sequence

Phases below are independently shippable. Each phase ends with a working, committed state.

### Phase 0 — Spikes (essential, ~3 days)

Bar for proceeding to dependent phases: a pass/fail call per spike, in writing.

1. **MinerU 2.5-Pro** on the user's real Arabic input from `input/`. Run against representative pages:
   - region count vs current pipeline
   - text accuracy (manual diff on 3 pages)
   - reading order on any 2-col Arabic pages present
   - latency per page on user's hardware
2. **Gemma 3 27B Q4_K_M** via llama.cpp on 10 already-solved pages from workspace. Side-by-side read of ar→tr output vs current Gemini/Groq output.
3. **Typst 0.14** with Arabic test fixture, comparing output to XeLaTeX on the same source.

Output: `notes/2026-05-12-spikes.md` with pass/fail per axis. Subsequent phases that depend on a failed spike are deferred or descoped.

### Phase 1 — Cloud opt-in flip (~3 days)

Smallest change, highest local-first value, no removal.

- Config top-level: `allow_cloud: false` (default).
- `internal/provider`: filter out cloud providers from the failover chain when `allow_cloud=false`. Local providers (Ollama, future llama.cpp/MLX) and no-op providers always allowed.
- `mutercim status` reports whether cloud is allowed and which providers in the chain are cloud-class.
- Cloud providers tagged with `class: cloud` in the provider registry; local providers tagged `class: local`. Tagging is internal; user config keeps current shape.
- Backwards-compat: existing user configs work as-is. The default flip from "cloud-allowed implicitly" to "cloud-allowed only when set" is the breaking change — document in CHANGELOG.

### Phase 2 — uv-managed Python tool helper (~1 week)

Add `uv` as an *alternative* backend for the 3 Python tool images. Old Docker paths stay default.

- `internal/pyhelper/`: install/start/stop/communicate with a uv-managed Python tool. Each tool gets its own `pyproject.toml` + `uv.lock` under `python-tools/<tool>/`.
- For each existing Docker-wrapped Python tool (Surya, DocLayout-YOLO, Qari-OCR):
  - Add `backend: docker | uv` config field, default `docker`.
  - `uv` backend invokes the tool's CLI via `uv run` against the pinned env.
  - Tool's HTTP/IPC contract is unchanged — only how the process is spawned differs.
- `Taskfile.yml`: new tasks `task py:bootstrap` (install uv, set up envs) and `task py:check` (verify all envs resolve).

After Phase 2 ships, the user can flip `backend: uv` per tool and side-by-side benchmark before any Docker removal.

### Phase 3 — Local translation providers (~1 week)

Add llama.cpp and MLX-LM as new providers behind the existing `Provider` interface. Cloud providers untouched.

- `internal/provider/llamacpp`: launches/connects to a `llama-server` instance, OpenAI-compatible HTTP. Marked `class: local`.
- `internal/provider/mlx`: launches/connects to `mlx-lm`'s OpenAI-compatible server on Apple Silicon. Marked `class: local`.
- Config templates with sane defaults per platform tier:
  - 8 GB VRAM: `gemma-3-12b-it-qat-q4_0` (llama.cpp) / `mlx-community/gemma-3-12b-it-4bit` (MLX)
  - 24 GB VRAM: `gemma-3-27b-it-q4_K_M` / `mlx-community/gemma-3-27b-it-4bit`
- Chunking to ≤2k input tokens regardless of context window — long-context translation quality degradation is a documented finding (BABILong-ITA, arXiv 2509.17249).
- These providers slot into the existing failover chain. With `allow_cloud: false` (Phase 1 default), only local providers stay in the chain.

### Phase 4 — Parse phase as alternative path (~1.5 weeks)

Add new `parse` phase that does what cut+layout+ocr+read does in one model call. Old four phases remain runnable and remain the default.

- `internal/parse/` package with two backends:
  - `vlm` — MinerU 2.5-Pro via MinerU 3.1.x toolkit (Apache-2.0-equiv, 1.2B, 8 GB VRAM, MLX-native, 109 langs).
  - `pipeline` — MinerU's pipeline backend, used for tail languages, CPU-only, or when VLM regresses on a specific input.
- New config block `parse: { backend, model, ... }`.
- New CLI command `mutercim parse`. Runs standalone over `cut/<input>/NNN.png` (or PDFs directly via MinerU) and emits `parse/<input>/NNN.json` in the existing region-based schema.
- New mode flag on `mutercim all`: `--mode=multi-phase` (default, runs current `layout → ocr → read`) or `--mode=parse` (runs the new single-call path).
- Schema mapping: MinerU's `Caption / Footnote / Formula / List-item / Page-footer / Page-header / Picture / Section-header / Table / Text / Title` → existing `header / entry / footnote / table / image / margin_note / page_number / column_header / separator / other`. Thin remap helper, well-tested.
- After Phase 4 ships, side-by-side `--mode=multi-phase` vs `--mode=parse` on real workload. No default change yet.

### Phase 5 — Language-agnostic plugin surface (~3-5 days)

Move Arabic-specific defaults out of core. RTL handling, Qari OCR routing, and Adab prompt corpus become a *plugin* loaded only when source language is `ar`.

- `internal/lang/<code>/profile.go`: per-language profile interface with optional hooks:
  - `ScriptDetect(text) bool` — does this region's script match this language
  - `OcrOverride()` — preferred OCR tool for pages identified as this language
  - `PromptCorpus()` — extra prompt knowledge to inject during translate
  - `ReadingOrderFixup(regions) regions` — post-process geometry-based reordering
  - `RenderingHints()` — RTL flag for LaTeX/Typst/docx writers
- `internal/lang/ar/`: wires up current Arabic-specific behavior (Qari OCR, Adab corpus, RTL render, optional 2-col geometry reordering). One file, contained.
- Default profile is empty. Pipeline picks up profiles via source language code in the input declaration.
- Other languages can add profiles without touching core code — directly addresses the "language-agnostic vision" goal.

The Arabic two-column geometry fixup lives here, not in the parse phase. It's not a P0, but it's free to include because the plugin scaffolding is required anyway.

### Phase 6 — Rendering alternatives (~1 week)

Add alternatives to XeLaTeX and Docker-pandoc; old paths remain default.

- `write.pdf_engine: xelatex | typst` (default `xelatex`).
  - `internal/render/typst`: Typst 0.14 via `typst` system binary or `typst-py` through pyhelper.
  - Templates are language-aware via the Phase 5 plugin (`ar` profile sets `dir: rtl`, kashida justification, etc.).
- `write.docx_engine: docker-pandoc | uv-pypandoc` (default `docker-pandoc`).
  - `uv-pypandoc` uses `pypandoc-binary` 1.17+ wheel (pandoc inside Python wheel, no system install) via pyhelper.
- `write.cut_engine: docker-poppler | system-pdftoppm | pymupdf` (default `docker-poppler`).
  - When parse phase (Phase 4) accepts PDFs directly, cut may be skippable; keep the option open via `cut.skip: bool`.

### Phase 7 — Docs / PLAN.md update (~2 days)

- Update README: pipeline diagram shows both the granular (7-phase) and shortcut (parse-collapsed) paths. CLI table shows the new commands and flags.
- Update `CLAUDE.md`: new conventions (uv-managed Python tools live under `python-tools/<tool>/`, local-first default with cloud opt-in, language profiles under `internal/lang/`).
- Update `docs/DECISIONS.md`: one-line entries for each phase that shipped, with rationale link to this file.
- Demote / promote items in `PLAN.md`: P5-1 (three-layer prompt customization) becomes part of Phase 5's language profile; P5-6 (parallel processing) stays. P5-10 (`unoffice`) deleted — research showed not viable.

## What this plan does *not* do (deferred)

- Remove Docker for Surya / DocLayout-YOLO / Qari-OCR (kept as an option until uv path proven on user's hardware).
- Remove old cut/layout/ocr/read phases (kept until parse phase proven on user's real workload).
- Remove XeLaTeX (kept until Typst quality proven equivalent).
- Implement parallel page processing within a phase (P5-6) — orthogonal, separate plan.
- Side-by-side bilingual PDF (P5-7) — orthogonal, separate plan.

These all become candidates for a follow-up cleanup PR after the user has run the new paths on their real workload and made a call per item.

## Open questions to answer mid-plan (not blockers)

1. Does MinerU's region-category enum need a 1:1 map to the current schema, or does the schema need to grow new categories? Answer comes from Phase 4 implementation.
2. Does `cut` collapse into `parse` cleanly? If MinerU accepts PDFs end-to-end, the page-image step may not need a dedicated phase. Decide during Phase 4.
3. Does the user prefer per-input or global cloud opt-in? Phase 1 starts global; revisit if real use cases want per-input granularity.
