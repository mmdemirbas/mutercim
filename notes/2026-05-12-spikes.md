# Phase 0 spikes — pass/fail gates the rest of the plan

## Baseline observations (before any spike)

Re-read of the existing `example/output/Anfas1/` artifacts on page 200
("الأَنفاس / حرز الأَلف مع الصاد"):

1. **Layout phase output quality**: DocLayout-YOLO at confidence 0.15, IoU
   0.25, image_size 2048 — emits ~40+ regions but classifies **every body
   entry as `footnote`** (raw_class: "split"). Body content is structurally
   numbered Sufi entries `(ت : صح ١٤٦٨) ...`, not footnotes. This is a
   classification failure on a non-standard layout.
2. **Read phase output quality**: read/200.json has
   `regions: null, reading_order: null`. Only `raw_text` is populated — the
   AI (openrouter qwen2.5-vl-72b free tier) returned JSON wrapped in
   ```` ```json ``` ```` fencing and the Go parser kept the raw fenced
   string instead of extracting the JSON. This is a known failure mode that
   already costs quality on page 200.
3. **No solve/translate/write output** exists — the pipeline was never run
   end-to-end for this input. So:
   - There is no baseline translation to compare local-Gemma against.
   - There is no baseline rendered PDF to compare Typst against.
   - There IS a baseline read-phase region structure (degraded but real) to
     compare MinerU against.
4. **The example config has `translate.languages: [ar]`** which is
   degenerate (ar→ar). Treating this as a placeholder. Real target for the
   spike: **ar→tr** (user is Turkish; Anfas is a classical Arabic Sufi text;
   Turkish translation is the natural target).

This baseline observation reframes the spikes. The bar is **not** "match the
current pipeline" — the current pipeline is itself degraded on this input.
The bar is "produce structurally-correct region JSON, with at least the same
text content captured, and ideally classified more usefully."

# Spike 1 — MinerU 2.5-Pro on Anfas1.pdf
status: in-progress — first attempt failed, pivoting backend

## Setup

- `uv venv --python 3.12 && uv pip install "mineru[core]"` succeeded
  cleanly. Pinned versions: torch 2.11.0, torchvision 0.26.0,
  transformers 4.57.6, mineru → bundled CLI.
- 5 test pages cut from `example/Anfas1.pdf` at 300 DPI into
  `notes/spike/data/pages/p-{050,100,200,300,400}.png`.
- Visual inspection of page 200: top half = numbered Sufi entries in a
  2-column-ish right-number-left-text shape, mid separator, bottom half =
  footnote prose with hadith references.

## Attempt 1: `vlm-auto-engine` backend — FAILED

Command: `mineru -p ./Anfas1.pdf -o ./out -s 199 -e 199 -l arabic -b vlm-auto-engine`

What happened:
1. Model download: 13 files, ~5 min total, the 1.2B safetensors took ~5 min
   on its own.
2. Backend selected: **transformers** (not MLX), despite Apple Silicon host.
3. GPU memory detection misreported: `gpu_memory: 1 GB, batch_size: 1` on
   an M1 Max 64 GB unified-memory host.
4. Layout phase succeeded.
5. Extraction phase ran 15 of 27 regions over ~10 minutes, with per-region
   time growing from ~3 s to ~130 s as memory pressure built.
6. Crashed at region 15 with no partial output saved.
7. Total wall time: 33 min 40 s for one page that didn't even complete.

Root cause hypothesis: MinerU's transformers-backed VLM path does not
handle Apple Silicon MPS memory correctly. It treats MPS as a 1 GB device,
defaults to single-batch, then fills allocator until the page collapses.
The "MLX backend for Apple Silicon" the research cited as a 2.5-Pro
shipping feature is **not** the default and apparently not auto-selected
by `vlm-auto-engine` — needs an explicit opt-in path.

## Attempt 2: `pipeline` backend — in progress

Per MinerU's own docs and the research note that the pipeline backend has
broader language coverage and lower VRAM (CPU-viable), this is the
fallback path. Running now.

## Implication for Phase 4 of the plan if VLM doesn't work locally

The research recommendation "MinerU 2.5-Pro VLM via MLX on Apple Silicon"
is **not validated** so far. Real options for Phase 4 become:

1. MinerU pipeline backend on Apple Silicon — verified after Attempt 2.
2. MinerU VLM via MLX — needs explicit `[mlx]` extra.
3. Switch primary parse-engine recommendation to dots.mocr or
   PaddleOCR-VL-1.5 (research listed both as MLX-friendly).
4. Run MinerU VLM remotely.

## Attempt 2 (corrected): VLM + MLX extras — STRUCTURE OK, ARABIC TEXT BAD

After `uv pip install "mineru[mlx]"` (adds mlx-vlm + mlx; bumps transformers
to 5.x — important version conflict, see Attempt 3 below):

- Re-ran `mineru -b vlm-auto-engine`. Engine line in logs:
  `Using mlx-engine as the inference engine for VLM.`
- Model load: **2.4 s** (vs 340 s on transformers — 142× faster).
- **28 regions extracted in 22 s** (vs the 9 min crash before).
- Total wall: **58 s** for one full Anfas page.

But the **text output is corrupted on Arabic**:

- Sufi entry numbers wrong: MinerU produced 1045, 1040, 1040, 1047 — the
  actual page numbers visible in the image are 1530, 1531, 1532, 1533.
- Chinese "炎症" (inflammation) inserted inside Arabic text — language
  fallback collision.
- Latin words like "Jeans", "nigي", "carbohydrates" intermixed with Arabic.
- Verb misreads: "أَصْبَتَ" produced instead of "أَصبَحتُ" (different verbs
  in classical Arabic).

The layout overlay PDF MinerU produced visually matches the page well —
**region detection is excellent**, every body entry and footnote correctly
boxed and numbered. It's only the OCR-into-text step on Arabic that fails.

This is the **narrow-language-coverage** caveat the research mentioned for
the VLM backend ("VLM backend is narrower than pipeline for tail languages").
For Arabic specifically, classical Arabic with diacritics, it falls back to
its dominant (CJK/Latin) training distribution.

## Attempt 3: pipeline backend in clean venv + offline mode — RUNS, but 2-COL FAILS

- VLM + Pipeline extras can't coexist in one venv (`[mlx]` upgrades
  transformers to 5.x; pipeline backend's MFR submodel calls
  `find_pruneable_heads_and_indices` removed in 5.x). **Real Phase 4 finding**:
  two separate uv venvs needed to support both MinerU backends.
- Created `.venv-pipeline` with `mineru[pipeline]` only. Pre-downloaded the
  PDF-Extract-Kit-1.0 model (14 GB, 184 files) via `hf download` to bypass
  the parallel-fetch semaphore-leak crash, then ran offline with
  `HF_HUB_OFFLINE=1`.
- Total wall: **37 s** (incl. 7 s model load).
- Backend log line: `OCR-det arabic: 5 regions` — pipeline has an explicit
  per-language OCR dispatch (this is what makes it good for Arabic in
  principle).

### Result on Anfas page 200 (single-column footnote section)

Numbers correct (1531, 1532, 1533, …, 1537). Hadith references correct
format `(خ 6639 ، م ، ت : صححه ، د)`. Prose readable. Diacritics largely
stripped vs the page image, but content captured.

### Result on Anfas page 200 (top body section with 2-column entries)

**Garbled**. The body block was treated as a single region, and the
right-to-left two-column reading was processed left-to-right:

```
ً ض 1531( ا ع ت بػ طَأْ أَخ ً و ضا ع ت بػ ب أَ  1534( دع ت يا س ب أَ
1535( ة عاِوي ت يا م ب أَ 1531( ْك ت ح ب أَ ِهم يِف اهللِ م
)1536تم ب أَ ت 1532(ْنس أَح ت ، و ب أَ
```

Numbers (1531, 1534, 1535, 1531, 1532, 1536) scattered and inter-fragmented
with word pieces.

### Result on Anfas page 100 (same structural shape as 200)

**Same pattern.** Body table garbled, footnotes clean. Confirms the failure
is **systematic for Anfas 2-col body sections**, not a page-200 anomaly.

### Reading-order overlay analysis

Pipeline's PP-DocLayoutV2 segments the body block as **one region**, then
runs OCR-det inside it without RTL/column awareness. DocLayout-YOLO in the
current pipeline segments **each entry individually** (~40 regions on page
200), which is finer but the AI vision LLM downstream had its own JSON-
parsing failure. Two different failure modes on the same content.

## Spike 1 verdict

**The Phase 4 plan's premise — "MinerU 2.5-Pro replaces cut+layout+ocr+read
as a single parse phase" — is NOT VALIDATED on this user's real workload.**

Detailed:

| Aspect | MinerU VLM (MLX) | MinerU pipeline | Current pipeline (DocLayout+Qari+AI) |
|---|---|---|---|
| Layout granularity | Fine (28 regions on p200) ✅ | Coarse (5 regions on p200) ❌ | Fine (40+ regions on p200) ✅ |
| Arabic text accuracy | Wrong numbers + Chinese contamination ❌ | Mostly correct on prose ✅ | Qari = high (Qari WER 0.16 / CER 0.06 per spec) ✅ |
| 2-col RTL reading order | Layout boxes correct but text mapping unverified | Broken systematically ❌ | DocLayout fine-grained avoids the problem ✅ |
| Apple Silicon native | Yes via MLX (2.4 s load) | CPU/MPS, model load 7 s | Docker-bound today |
| End-to-end wall on p200 | 58 s | 37 s | n/a (the existing baseline never produced solve/translate/write) |
| Install footprint | ~7 GB | ~14 GB | ~5 GB Docker images |

**Implications for the plan:**

1. **Phase 4 (collapse parse phase) — DEFERRED, not killed.** A MinerU
   front-end might still pay off for the rough layout pass, but it cannot
   replace the high-quality Arabic OCR step.
2. **Realistic Phase 4 shape**: keep the multi-phase structure, but allow
   per-input selection between (a) MinerU pipeline backend (covers
   layout+OCR for non-Arabic in one call) and (b) DocLayout-YOLO + Qari
   (current, Arabic-strong). This is *less* aggressive than the original
   plan but matches the user's stated principle "don't remove until
   proven better."
3. **The Arabic 2-col reading-order fixup in Phase 3 of the plan becomes
   load-bearing**, not optional. Every option open here has the same gap.
4. **Two separate uv venvs needed** for MinerU's two backends (transformers
   version conflict). Phase 2 of the plan should plan for one venv per
   Python tool, not one global venv.
5. **dots.mocr / PaddleOCR-VL alternatives** worth probing in a follow-up
   spike before declaring MinerU the wrong path. They might have the
   layout-VLM strengths without the Arabic text corruption.

# Spike 2 — Gemma 3 27B IT 4-bit (Arabic → Turkish translation)
status: **PASS**

## Setup

- Downloaded `mlx-community/gemma-3-27b-it-4bit` via `hf download` into
  `notes/spike/gemma/gemma-3-27b-it-4bit/` — 16 GB across 4 safetensor
  shards + tokenizer.
- Used the existing MinerU `[mlx]` venv (already has `mlx-lm` from the
  `mineru[mlx]` install) — no separate Python env needed.
- Test inputs from `example/output/read/Anfas1/200.json`'s raw_text — real
  Anfas content: 1 chapter heading, 2 Sufi entries, 1 footnote prose.
- System prompt in Turkish instructing a Sufi/Islamic-aware classical
  Arabic → Turkish translator.

## Run

```
python translate-test.py
```

Performance on M1 Max 64 GB:
- Model load (~16 GB Q4 weights): **13.5 s**
- Inference per input: **13.7 s** (heading, ~25 tokens out) / **14.7 s**
  (one-line entry) / **21.3 s** (longer entry) / **44.1 s** (footnote prose,
  ~250 tokens out)
- Effective throughput: ~5-6 tokens/sec.

## Quality

Concrete output samples (full output in
`/private/tmp/.../bum8sykh0.output`):

- **Sufi entry 1530** (input: "أَصبَحتُ بِصُحْبَةٍ أَبَداً أَخُفُّهُمُ حُكماً وَأَحسَنُهُمُ نَفساً")
  → "Ebediyen, hükümde en hafifleri ve nefisçe en güzel olanların
  refakatinde sabahladım." Accurate, idiomatic Turkish, captures the Sufi
  meaning. Minor diacritic-info loss vs original but semantically faithful.

- **Sufi entry 1532** (input with two parallel "فطوبى لمن" clauses)
  → "...O halde, güzel işler yapana ve kimseyi incitmeyene ne mutlu! Ve
  rızkı kendisine yeterli olana, evine bağlı kalana ne mutlu!" — "ne mutlu"
  is the natural Turkish rendering of "tooba" (blessed/happy). Reads like
  published Islamic Turkish.

- **Footnote 1530** (hadith narrative)
  → Idiomatic Turkish with culturally appropriate honorifics inserted:
  "Peygamber Efendimiz (s.a.v.)" for "النبي ﷺ", "Hz. Ebubekir (r.a.)" for
  "أبو بكر". One slight ambiguity in who-asked-whom but the original Arabic
  is also ambiguous.

## One concrete weakness

- **Chapter heading** "حرز الأَلف مع الصاد" → "Bin ile Sin'in koruması."
  Wrong. The original is a chapter title indicating alphabetical
  organization: "[entries whose first letter is] Alif together with [last
  letter] Sad". Gemma confused the Arabic letter names "Alif" and "Sad"
  with the homophone meanings "thousand" and the personal name "Sin/Sad".
  Solvable via glossary context (the user's existing knowledge layer
  injection) or a per-chapter-heading dedicated prompt.

## Spike 2 verdict

**Local Gemma 3 27B IT 4-bit via MLX is publication-quality for Sufi/Islamic
Arabic → Turkish on M1 Max 64 GB.** No cloud needed for translation quality.
Phase 3 of the plan (local translation providers via llama.cpp / MLX-LM) is
validated for the user's primary use case.

Performance is **batch-acceptable, not real-time**:
- 100-page book ≈ 2000 translatable units ≈ ~8 hours of inference at
  current rates. Fine for an overnight workflow, not for interactive use.
- For faster turn-around: Gemma 3 12B IT QAT-Q4 at T1 budget (~7 GB) should
  give ~12 tokens/sec on the same hardware. Worth follow-up spike if speed
  becomes an issue.

## Time spent on Spike 2

- Model download: ~40 min (16 GB, throttled, unauthenticated HF)
- Test script + inference: ~3 min
- **Total**: ~43 min

2. **Gemma 3 12B IT QAT-Q4 throughput at T1**. Would tell us whether the

4. **MinerU VLM + Qari OCR overlay** — using MinerU's strong layout
   detection but replacing its OCR text per-region with Qari output. If
   this works, MinerU layout could replace DocLayout-YOLO entirely.
